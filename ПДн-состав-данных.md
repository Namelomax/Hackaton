# Состав обрабатываемых данных — «Протоколер» + анонимизатор

Документ для анкеты хостинг-провайдера и для акта определения уровня защищённости
ИСПДн по ПП РФ № 1119. Составлен по фактическому коду, а не по замыслу.

---

## Краткий ответ для анкеты

| Параметр (ПП 1119) | Значение |
|---|---|
| Категория ПДн | **Иные**, с риском попадания **специальных** (см. раздел 4) |
| Биометрические ПДн | Нет — при условии, что аудиозаписи не загружаются (см. раздел 4) |
| Категория субъектов | Не сотрудники оператора (участники совещаний, контрагенты) |
| Количество субъектов | Менее 100 000 |
| Тип актуальных угроз | 3-й (обоснование спорно, см. раздел 4) |
| **Заявляемый уровень защищённости** | **УЗ-3** |

УЗ-3 выбран сознательно, а не по букве матрицы. Формально «иные ПДн + 3-й тип
угроз + менее 100 000 субъектов» дают УЗ-4, но система принимает свободную речь
и не может гарантировать отсутствие специальных категорий, а стек содержит
иностранное несертифицированное ПО. Оба фактора при проверке поднимают уровень
до УЗ-3, и разница в требованиях — одно назначение ответственного за
безопасность ПДн. Закладывать сразу дешевле, чем переаттестовываться.

## 1. Данные в СУБД (постоянное хранение)

СУБД: SurrealDB. Таблицы и их содержимое:

### 1.1. `anonymization_mappings` — критичная таблица

Самый чувствительный объект системы. Хранит на одну беседу:

| Поле | Содержимое | Категория |
|---|---|---|
| `mapping` | Таблица соответствий `[PERSON_1] → Иванов Иван Иванович`, `[ORG_2] → ООО «Ромашка»`, `[INN_1] → 7707083893` | Иные ПДн, **в открытом виде** |
| `counters` | Счётчики плейсхолдеров по типам | Не ПДн |
| `document_json` | Последний валидный Protocol JSON **с реальными данными** (нужен для точечных правок) | Иные ПДн |
| `preview` | Анонимизированный текст, показанный пользователю | Псевдонимизированные ПДн |
| `updated` | Дата изменения | Не ПДн |

Ключевой момент: наличие `mapping` означает, что обработка является
**псевдонимизацией, а не обезличиванием** в смысле ст. 3 п. 9 152-ФЗ.
Псевдонимизированный текст остаётся персональными данными, потому что
восстановление возможно при наличии дополнительной информации — и эта
информация лежит в соседнем поле той же записи.

### 1.2. `conversations`

| Поле | Содержимое | Категория |
|---|---|---|
| `userId` | Ссылка на пользователя | Иные ПДн |
| `title` | Название беседы (часто = тема совещания) | Иные ПДн |
| `messages`, `messages_raw` | **Полная переписка, включая исходную расшифровку совещания в открытом виде** | Иные ПДн, риск специальных |
| `document_content` | Текст сформированного протокола | Иные ПДн |

### 1.3. `users`

`username`, `usernameLower`, `passwordHash`. Иные ПДн + аутентификационные
данные. Пароли хранятся в виде хеша.

### 1.4. `prompt`, `protocol_examples`, инструкции по протоколам

Тексты системных промптов и **примеры ранее составленных протоколов**,
сохраняемые для few-shot подсказок модели. Примеры берутся из реальных
документов, поэтому содержат реальные ПДн, если их не чистить.

## 2. Данные на сервере анонимизатора

| Объект | Содержимое | Хранение |
|---|---|---|
| Очередь задач `_JOBS` (ОЗУ) | Исходный текст документа, результат, mapping, спаны | Оперативная память, TTL 10 минут после завершения |
| Тело HTTP-запроса `/anonymize` | Исходный текст или .docx в base64 | Транзитно, на диск не пишется |
| `custom_terms.txt` | Глоссарий терминов, всегда подлежащих маскированию | Постоянно на диске; может содержать ФИО и названия организаций |
| Веса моделей (GLiNER, gemma) | — | Не ПДн |

Документы на диск сервер не сохраняет: `.docx` собирается в памяти и
возвращается в ответе.

## 3. Журналы (логи)

**Логи содержат персональные данные.** Это надо учитывать при выборе хостинга
и при настройке доступа к журналам.

Модуль `anonymizer/review.py` печатает в stderr реальные значения:

| Место | Что попадает в лог |
|---|---|
| `review.py:451` | Имена и позывные, оставленные замаскированными после adjacency-проверки |
| `review.py:457` | Слова, с которых маска снята |
| `review.py:608` | Короткие числа, оставленные замаскированными |
| `review.py:971` | Примеры кандидатов, найденных recall-проходом |
| `review.py:1011` | **Сырой ответ LLM, первые 600 символов** — может содержать любые ПДн |

Журналы приложения дополнительно пишут идентификаторы бесед и количество
записей в mapping.

Практический вывод: журналы приравниваются по чувствительности к самим данным,
хранятся в том же защищённом контуре, доступ к ним ограничивается. Для УЗ-2 это
и так обязательное требование, для УЗ-3 — разумная предосторожность.

## 4. Факторы, повышающие уровень защищённости

### 4.1. Специальные категории в свободной речи

Расшифровка совещания — неконтролируемый ввод. Фразы вида «он на больничном»,
«она в декрете», «у него инвалидность» вносят в систему данные о здоровье, то
есть специальную категорию. По ПП 1119 при смешении категорий применяется
наиболее строгая: вся ИСПДн классифицируется как обрабатывающая специальные
ПДн. При 3-м типе угроз это даёт **УЗ-3**, при 2-м типе — **УЗ-3**, при более
чем 100 000 субъектов и 2-м типе — **УЗ-2**.

Митигация: организационная. В политике обработки зафиксировать запрет на
обсуждение сведений о здоровье и убеждениях в загружаемых расшифровках; при
превышении — обрабатывать как специальные.

### 4.2. Тип актуальных угроз

3-й тип означает отсутствие оснований подозревать недекларированные возможности
в ПО. В контуре присутствуют: gemma-4-12b (закрытые веса, зарубежный
разработчик), LM Studio, GLiNER, SurrealDB, при облачном режиме — OpenRouter.
Всё это несертифицированное иностранное прикладное ПО, что даёт основания
настаивать на **2-м типе угроз** (НДВ в прикладном ПО). Тогда даже категория
«иные» даёт **УЗ-3**.

Обоснование выбранного типа угроз обязательно фиксируется в Модели угроз.

### 4.3. Биометрия — пока нет, но легко появится

Сейчас система принимает текстовые расшифровки, поэтому биометрических ПДн нет.
Если добавится загрузка **аудиозаписей совещаний**, голос станет биометрическим
персональным данным, и уровень скачет: биометрия при 3-м типе угроз — сразу
**УЗ-3** независимо от объёма, при 2-м типе — **УЗ-2**. Плюс потребуется
письменное согласие каждого субъекта.

## 5. Требования к площадке

Исходя из состава данных:

1. **Размещение на территории РФ** — ч. 5 ст. 18 152-ФЗ требует, чтобы запись,
   систематизация, накопление и хранение ПДн граждан РФ велись в базах данных на
   территории России. Это касается в первую очередь СУБД с таблицей
   `anonymization_mappings`.
2. **Аттестованная площадка под УЗ-3** — провайдер должен подтверждать
   соответствие приказу ФСТЭК № 21 для 3-го уровня и предоставлять аттестат.
3. **Сертифицированные СЗИ** — средства защиты с оценкой соответствия ФСТЭК
   (5-й класс для УЗ-3).
4. **Раздельное хранение** — правила обезличивания, действующие с 1 сентября
   2025, запрещают хранить обезличенные данные вместе с исходными. Сейчас
   `mapping` и `preview` лежат в одной записи; это стоит разнести.
5. **Договор поручения обработки** с провайдером по ст. 6 ч. 3 152-ФЗ.
6. **Шифрование** резервных копий и хранилища СУБД.

## 6. Отдельно: трансграничная передача

Два канала, по которым данные покидают контур:

- **Облачная LLM** (OpenRouter и подобные) — туда уходит псевдонимизированный
  текст. Функция `scan_residual_pii` возвращает предупреждения об остаточных
  ПДн, то есть система сама фиксирует, что анонимизация не стопроцентна.
  Формулировка «данные не уходят в облако» некорректна.
- **Хостинг СУБД** — если инстанс расположен за пределами РФ.

Оба случая требуют уведомления Роскомнадзора о трансграничной передаче до её
начала (ст. 12 152-ФЗ) и учитываются при выборе площадки.
