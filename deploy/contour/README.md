# Установка Протоколера в контуре компании

Протоколер целиком работает внутри вашей инфраструктуры: приложение, база
данных и языковая модель — на ваших серверах, данные наружу не уходят.

Этот же файл лежит в корне комплекта для переноса (см. шаг 1) — инструкция
одна и та же, где бы вы её ни открыли.

## Что входит в установку

| Сервис | Нужен | Что делает |
|---|---|---|
| `web` | всегда | приложение (Next.js), порт 3000 |
| `surrealdb` | всегда | база данных: пользователи, чаты, протоколы, папки |
| `ollama` | по выбору | языковая модель, если своего LLM-сервера нет; нужна видеокарта NVIDIA |

Языковая модель — единственная внешняя для приложения часть. Подойдёт ваш
LLM-сервер (vLLM, Ollama, шлюз) или встроенный контейнер `ollama`. Подробно —
в разделе [«Подключение языковой модели»](#3-подключение-языковой-модели).

## Перед установкой

1. **Языковая модель.** Решите, где она будет работать — от этого зависят
   настройки. Варианты: встроенная Ollama, свой vLLM, другой
   OpenAI-совместимый сервер. Требования к модели — в разделе 3.
2. **Сервер.** Linux, Docker Engine 24+ и Compose v2. Для встроенной Ollama
   дополнительно NVIDIA Driver и NVIDIA Container Toolkit.
3. **Доступ в интернет.** Если в контуре есть доступ к Docker Hub и npm (или
   к их внутренним зеркалам), образы собираются прямо на месте. Если нет —
   собираются снаружи и переносятся файлом.
4. **Домен и TLS.** Наружу приложение публикуется через ваш reverse-proxy
   (nginx и т.п.) на `127.0.0.1:3000`. Обязательно `proxy_buffering off` —
   протокол приходит потоком по SSE — и `client_max_body_size 50m` для
   загрузки расшифровок.

## 1. Сборка образов

### В контуре есть доступ в интернет

Из корня репозитория:

```bash
docker compose build
```

### Интернета в контуре нет

Собрать комплект на машине с интернетом и Docker, из корня репозитория:

```bash
scripts/contour/bundle-images.sh                  # web + surrealdb
scripts/contour/bundle-images.sh --with-ollama    # + образ ollama
```

Получится каталог `dist/protokoler-contour-<дата>-<коммит>/`: образы, файлы
запуска, шаблон `.env`, служебные скрипты и эта инструкция. Каталог целиком
переносится в контур.

Модели Ollama в комплект не входят — их перенос описан в варианте А раздела 3.

## 2. Первый запуск

Если переносили комплект — распакуйте его и загрузите образы:

```bash
cd /opt/protokoler                         # куда распаковали комплект
sha256sum -c SHA256SUMS
docker load -i images.tar.gz
cp env.contour.example .env
```

Если собирали из репозитория — шаблон лежит в `deploy/contour/`:

```bash
cp deploy/contour/env.contour.example .env
```

Заполните в `.env` обязательные поля: `SURREALDB_PASSWORD`, `SESSION_SECRET`,
`ADMIN_USERNAMES` — и настройки языковой модели по разделу 3. Пароль БД
задаётся до первого запуска: база создаётся с ним, и сменить его потом можно
только вручную.

Если будете переносить данные из облачной версии, сначала поднимите только
базу и выполните раздел 4:

```bash
docker compose up -d surrealdb
```

Свежая установка без переноса данных:

```bash
docker compose up -d
curl -s http://127.0.0.1:3000/api/health/db
```

Откройте сайт, нажмите «Первый вход администратора» и зарегистрируйте логин
из `ADMIN_USERNAMES`. Самостоятельной регистрации нет — остальных
пользователей заводит администратор на `/admin`.

## 3. Подключение языковой модели

### Требования к модели

- **API** — OpenAI-совместимые `/v1/chat/completions` и `/v1/models`.
- **Модель** — класс Qwen3 на 14–30 млрд параметров. Рабочий стенд сейчас
  готовит протоколы на `Qwen3.8-27B`.
- **Окно контекста** — минимум 32 768 токенов, для длинных встреч 65 536.
  Промпт полуторачасовой расшифровки занимает около 32 тысяч токенов: при окне
  32 768 на сам протокол места не остаётся, и сборка падает с сообщением
  «Расшифровка слишком большая».

Названия переменных начинаются с `OLLAMA_` по историческим причинам — они
подходят для любого OpenAI-совместимого сервера.

### Вариант А. Встроенная Ollama

Подходит, если своего LLM-сервера в контуре нет. Нужна видеокарта NVIDIA.

```bash
OLLAMA_BASE_URL=http://ollama:11434/v1
OLLAMA_API_KEY=ollama
ALLOWED_OLLAMA_MODELS=qwen3:14b
OLLAMA_CONTEXT_LENGTH=32768
LLM_MAX_MODEL_LEN=32768

# Контейнер ollama и видеокарта — для всех команд docker compose сразу
COMPOSE_PROFILES=ollama
COMPOSE_FILE=docker-compose.yml:docker-compose.gpu.yml
```

В шаблоне последние две строки закомментированы — **раскомментируйте их**.
Они важнее, чем кажутся: без них контейнер `ollama` и видеокарту пришлось бы
включать флагами в каждой команде, и любой `docker compose up -d` без флагов —
например, при обновлении версии — пересоздал бы Ollama без видеокарты. Из
`.env` Compose читает их сам, и дальше достаточно обычного
`docker compose up -d`.

По умолчанию эти строки выключены намеренно: со своим vLLM или другим
сервером встроенная Ollama не нужна, а включённая — заберёт все видеокарты.

**Окно контекста задаётся двумя переменными, и менять их нужно вместе.**
`OLLAMA_CONTEXT_LENGTH` — окно самой модели, `LLM_MAX_MODEL_LEN` — окно, под
которое приложение рассчитывает длину ответа. Ollama не сообщает окно в
`/v1/models`, поэтому без `LLM_MAX_MODEL_LEN` приложение считает его равным
32 768, сколько бы ни стояло в `OLLAMA_CONTEXT_LENGTH`. Для длинных встреч —
65 536 в обеих; это требует больше видеопамяти.

**Загрузка модели при доступе в интернет:**

```bash
docker compose up -d ollama
docker compose exec ollama ollama pull qwen3:14b
```

**Без интернета** модель скачивается снаружи и переносится архивом. Снаружи:

```bash
ollama pull qwen3:14b
tar czf ollama-models.tgz -C ~/.ollama models
```

В контуре — распаковать прямо внутри контейнера `ollama` (других образов для
этого не нужно):

```bash
docker compose up -d ollama
docker compose cp ollama-models.tgz ollama:/tmp/
docker compose exec ollama tar xzf /tmp/ollama-models.tgz -C /root/.ollama
docker compose exec ollama rm /tmp/ollama-models.tgz
docker compose exec ollama ollama list            # модель должна появиться
```

### Вариант Б. Свой vLLM

Ключевые параметры запуска vLLM, от которых зависит работа приложения:

```bash
vllm serve Qwen/Qwen3-14B \
  --served-model-name qwen3-14b \
  --max-model-len 65536 \
  --reasoning-parser qwen3 \
  --api-key <ключ> \
  --host 0.0.0.0 --port 8000
```

Названия флагов зависят от версии vLLM — сверьтесь с документацией своей.

Настройки в `.env`:

```bash
OLLAMA_BASE_URL=http://<адрес-vllm>:8000/v1
OLLAMA_API_KEY=<значение --api-key>
ALLOWED_OLLAMA_MODELS=qwen3-14b          # ровно как --served-model-name
OLLAMA_CONTEXT_LENGTH=65536              # равно --max-model-len, не больше
LLM_FORCE_NONSTREAM=false
```

И **удалите строку `LLM_MAX_MODEL_LEN`** из `.env`, если скопировали её из
шаблона. vLLM сообщает окно в `/v1/models` (`max_model_len`), и приложение
подхватывает его само — в том числе если окно или модель потом поменяются.
Явное значение отключает это и закрепляет окно навсегда.

Что важно знать:

- **`OLLAMA_CONTEXT_LENGTH` не должен превышать `--max-model-len`.** По нему
  приложение рассчитывает, сколько истории чата поместится в запрос. Поставите
  больше реального окна — запрос переполнится, и vLLM ответит ошибкой
  `maximum context length`.
- **Рассуждения модели.** Протокол собирается как JSON, поэтому рассуждения
  модели не должны попадать в ответ. Приложение отключает их параметром
  `reasoning_effort: "none"` — это проверено на vLLM с Qwen3. Флаг
  `--reasoning-parser` подстраховывает: если рассуждения всё же появятся, vLLM
  положит их в отдельное поле, и JSON не сломается.
- **vLLM на той же машине, что и Docker.** Внутри контейнера `localhost` —
  это сам контейнер, а не сервер. Используйте
  `OLLAMA_BASE_URL=http://host.docker.internal:8000/v1` — этот адрес уже
  прописан для `web` в `docker-compose.yml`.
- **Имя модели** чувствительно к регистру. Если на сервере одна модель,
  приложение найдёт её само; `ALLOWED_OLLAMA_MODELS` решает, какую брать, когда
  моделей несколько.
- **Не включайте `LOCAL_TOOLS_ENABLED=true`**, если vLLM запущен без
  `--enable-auto-tool-choice` и `--tool-call-parser`. Такой vLLM отклоняет
  любой запрос с полем `tools` — падает не вызов инструмента, а весь запрос,
  включая обычное «Привет». По умолчанию инструменты выключены, и приложению
  они не нужны.

### Вариант В. Другой OpenAI-совместимый сервер

LiteLLM, Open WebUI, TGI, LM Studio, корпоративный шлюз и т.п. Совместимость у
таких серверов разная, поэтому настроек больше:

```bash
OLLAMA_BASE_URL=http://<адрес>/v1
OLLAMA_API_KEY=<ключ>
ALLOWED_OLLAMA_MODELS=<имя модели ровно как в /v1/models>
OLLAMA_CONTEXT_LENGTH=<реальное окно модели>
LLM_MAX_MODEL_LEN=<то же значение>
```

- **Окно — обе переменные.** Большинство таких серверов не сообщает окно в
  `/v1/models`, поэтому, как и с Ollama, нужен `LLM_MAX_MODEL_LEN`. Узнать
  реальное окно — у администратора сервера. Не завышайте: при переполнении
  сервер ответит ошибкой.
- **Сервер отвечает JSON вместо потока** — частая особенность шлюзов. Симптом:
  ответ приходит целиком в конце или не приходит вовсе. Поставьте
  `LLM_FORCE_NONSTREAM=true`.
- **Сервер отвечает 400 на лишние поля.** Если адрес похож на Ollama (порт
  11434 или слово `ollama` в адресе), приложение добавляет в запрос поля
  Ollama `think` и `keep_alive`. Строгие шлюзы на них падают — тогда
  `LLM_VENDOR_EXTENSIONS=none`.

### Проверка подключения

С хоста:

```bash
curl -s -H "Authorization: Bearer <ключ>" http://<адрес>/v1/models
```

Изнутри контейнера `web` — так видит сервер само приложение, с его сетью и
ключом:

```bash
docker compose exec web node -e "fetch(process.env.OLLAMA_BASE_URL+'/models',{headers:{Authorization:'Bearer '+process.env.OLLAMA_API_KEY}}).then(r=>r.text()).then(console.log)"
```

В ответе должна быть ваша модель. У vLLM там же видно `max_model_len` —
окно, которое возьмёт приложение.

## 4. Перенос данных из облачной версии

Нужен, если вы уже работали в облачной версии Протоколера и хотите сохранить
пользователей, чаты, протоколы, промпты и папки. Дамп облачной базы готовит
исполнитель: вы получаете файл `protokoler-<время>.surql` и манифест
`protokoler-<время>.surql.counts.json` для сверки.

Положите оба файла в каталог `backups/` установки и выполните:

```bash
docker compose stop web
scripts/contour/db-import.sh backups/protokoler-<время>.surql
docker compose run --rm --no-deps \
  -v "$PWD/scripts:/app/scripts:ro" -v "$PWD/backups:/backups:ro" \
  web node scripts/contour/db-counts.mjs --expect /backups/protokoler-<время>.surql.counts.json
docker compose up -d web
```

Сверка должна показать «все N таблиц совпали». `db-import.sh` импортирует
только в пустую базу. Чтобы повторить импорт с нуля, удалите том:
`docker compose down && docker volume rm forus-chatbot_surreal-data`.

Логины администраторов в `ADMIN_USERNAMES` укажите из перенесённой базы —
при входе они получат права администратора.

**В дампе персональные данные**: расшифровки, протоколы, ФИО участников.
Права на файл — 600. Не пересылайте его открытыми каналами (почта,
мессенджеры) и удалите с промежуточных машин после импорта.

**Переключение пользователей.** Согласуйте с исполнителем время: облачная
версия останавливается, исполнитель делает финальный дамп, вы импортируете его
и переключаете пользователей на адрес в контуре. Облачная база в процессе не
меняется, поэтому при неудаче облачную версию можно снова запустить.

## 5. Резервные копии

```bash
crontab -e
0 3 * * * cd /opt/protokoler && scripts/contour/db-backup.sh >> backups/backup.log 2>&1
```

Скрипт хранит 14 последних копий (`BACKUP_KEEP=30` — больше). Копии стоит
регулярно выносить на другой диск или сервер: бэкап на том же диске не спасёт
от потери диска.

Данные лежат в томе `forus-chatbot_surreal-data`. Имя проекта
(`COMPOSE_PROJECT_NAME`) на работающей установке не меняйте: новое имя создаёт
новые пустые тома.

## Обновление версии

Обновите исходники и пересоберите образы — в контуре (`git pull && docker
compose build`) или снаружи (`git pull && scripts/contour/bundle-images.sh`,
затем перенос). В контуре:

```bash
scripts/contour/db-backup.sh
docker load -i images.tar.gz               # если переносили комплект
docker compose up -d                       # пересоздаст контейнеры с новыми образами
```

Схема базы обновляется сама при старте.

## Неполадки

- **`web` не стартует: «Задайте SURREALDB_PASSWORD / SESSION_SECRET»** — не
  заполнен `.env`.
- **`/api/health/db` → 500** — смотрите `docker compose logs surrealdb`. Пароль
  в `.env` должен совпадать с тем, с которым база создавалась при первом
  запуске.
- **Ответы модели не приходят** — проверьте подключение изнутри `web`
  (раздел 3, «Проверка подключения»). Ответ целиком в конце или пустой
  ответ — `LLM_FORCE_NONSTREAM=true`.
- **«Расшифровка слишком большая»** — окно модели меньше, чем нужно для этой
  встречи. Увеличьте окно (раздел 3) или разбейте расшифровку на части.
- **`maximum context length`** — `OLLAMA_CONTEXT_LENGTH` больше реального
  окна модели. Поставьте его не больше окна сервера.
- **Ollama не видит видеокарту** — проверьте `COMPOSE_FILE` в `.env`
  (вариант А раздела 3) и что установлен NVIDIA Container Toolkit:
  `docker compose exec ollama nvidia-smi` должен показать карту.

### Пользователи «не сохраняются», логин приходится регистрировать заново

Учётные записи хранятся только в базе (таблица `users`), не в браузере:
`localStorage` помнит лишь, кто вошёл на этом устройстве. Почти всегда это
значит, что приложение смотрит не в ту базу.

1. **Не тот адрес БД.** Хост `surrealdb` существует только внутри Docker. При
   запуске приложения вне Docker адрес — `ws://127.0.0.1:8000/rpc`.
2. **Не тот том.** Том называется `<имя проекта>_surreal-data`, по умолчанию
   `forus-chatbot_surreal-data`. Сменили `COMPOSE_PROJECT_NAME` или каталог —
   получили новую пустую базу.

Проверка — тот же экземпляр, что использует `web`:

```bash
curl -s http://127.0.0.1:3000/api/health/db
```

Смотрите `surreal.namespace`, `surreal.database` и `userCount`. После
регистрации `userCount` должен стать ≥ 1. С другого компьютера откройте тот же
сайт и вызовите `/api/health/db` ещё раз — значения должны совпасть.

Напрямую в БД. Пароль берётся из `.env` — в оболочке хоста переменной
`SURREALDB_PASSWORD` нет, пока вы её сами не загрузите:

```bash
PASS=$(grep '^SURREALDB_PASSWORD=' .env | cut -d= -f2)
docker compose exec surrealdb /surreal sql \
  --endpoint ws://127.0.0.1:8000/rpc \
  --namespace chatbot --database main \
  --username root --password "$PASS"
```

```sql
SELECT id, username, usernameLower FROM users;
```

### SurrealDB: версия движка

Движок — SurrealDB **2.6.x**. Клиент `surrealdb` в приложении (ветка 1.x)
работает только с движком `>= 1.4.2 < 3.0.0`. С движком 3.x (`:latest`) в
логах `web` появится `UnsupportedVersion`.

**«The data stored on disk is out-of-date with this version»** — том создан
другой major-версией движка. Верните ту версию, что создавала данные, и
мигрируйте по [руководствам SurrealDB](https://surrealdb.com/docs), либо
начните с чистой базы (см. ниже).

### SurrealDB: `Permission denied` / RocksDB

`Failed to create RocksDB directory` в `docker compose logs surrealdb`. Для
`surrealdb` уже задано `user: "0:0"`, поэтому чаще всего дело в томе,
созданном раньше с чужими правами. Сначала:

```bash
docker compose up -d --force-recreate surrealdb
```

Не помогло — удалите том БД. **Это сотрёт все данные**, сначала сделайте
бэкап:

```bash
docker compose down
docker volume rm forus-chatbot_surreal-data
docker compose up -d
```
