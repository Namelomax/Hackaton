## 2. Реальная архитектура

Поток запроса (`app/api/chat/route.ts` → `agents/`):

1. `route.ts` принимает сообщения и файлы, извлекает текст вложений (PDF/DOCX/XLSX/PPTX) и кладёт его в `metadata.hiddenTexts` и в **системный блок чата** (`hiddenDocsContext`).
2. `main-agent.ts` маршрутизирует: если в последнем сообщении явная команда («сформируй протокол») → `document-agent`; иначе → `chat-agent` (с инструментом `publishInvestigationProtocol`).
3. `chat-agent.ts` ведёт диалог, видит расшифровку через системный промпт.
4. `document-agent.ts` (`generateFinalDocument`) собирает свой промпт из `uiMessages` и через `streamObject` получает JSON → валидирует Zod-схемой → рендерит markdown + DOCX.

Замечание: `classifier.ts`/`SGR_CLASSIFIER_PROMPT` и `orchestrator.decideNextAction` написаны, но **не используются** — роутинг идёт по regex и по tool-вызову. Это мёртвый слой (не баг, но мусор).

## 5. Что изменено в этом заходе (код)

Все правки — точечные и обратимые (git).

1. **`app/api/chat/agents/document-agent.ts`**
   - В `conversationContext` теперь подмешивается текст расшифровки из `metadata.hiddenTexts` с пометкой `[РАСШИФРОВКА ВСТРЕЧИ — первоисточник фактов для разделов 2 и 4]`. Есть мягкий лимит `DOC_MAX_TRANSCRIPT_CHARS` (по умолчанию 60000).
   - После валидации вызывается `mergeProtocolWithChatDraft(validated, chatDraft)` — добивает пустые разделы.
   - Затем `applyGlossaryToProtocol(validated)` — детерминированная зачистка жаргона.

2. **`lib/prompts/glossary.ts` + `data/glossary.json` (новые)**
   - Редактируемый словарь замен «жаргон → официально-деловая форма». Применяется regex-ом по границам слова (с учётом кириллицы), сохраняет регистр, не трогает ФИО и названия организаций.
   - Пополняется правкой `data/glossary.json` без пересборки (кэш с TTL). Это и есть «база», которую просил заказчик; в перспективе её сможет дополнять и сам ИИ (нужен отдельный tool — см. «Осталось»).

3. **`lib/ollama-limits.ts`**
   - Вменяемые дефолты: чат 4096, файловый ход 2048, протокол 8192 токенов. Добавлен глобальный потолок `ollamaHardCapOutputTokens()` (16384) — предохранитель.

4. **`lib/resolve-chat-model.ts`**
   - Потолок берётся из `ollamaHardCapOutputTokens()` (раньше из чат-дефолта — это резало генерацию протокола).
   - Стриминг управляется `LLM_FORCE_NONSTREAM` (по умолчанию `true` — текущее поведение для прокси JupyterHub). На vLLM/нормальном прокси поставьте `LLM_FORCE_NONSTREAM=false` → нативный стриминг, текст появляется по мере генерации.

5. **`lib/prompts/sgr-prompts.ts`** — `SGR_MAIN_AGENT_PROMPT` переписан с ~400 до ~70 строк: убраны дубли и противоречия, принцип «минимум вопросов одним блоком», подробное «Обсудили» для отсутствовавшего читателя, чёткий поток из 5 шагов. Документный промпт получил указание на метку расшифровки и формулировку «подлежит уточнению».

6. **`app/api/chat/agents/chat-agent.ts`** — строка «строго один вопрос за ответ» заменена на «минимум вопросов одним блоком» (устраняет жалобу про «по одному вопросу + Верно?»).

### Новые переменные окружения

```bash
# Стриминг (на vLLM включить нативный)
LLM_FORCE_NONSTREAM=false
# Лимиты вывода (есть разумные дефолты, менять не обязательно)

OLLAMA_PROTOCOL_MAX_OUTPUT_TOKENS=8192
OLLAMA_HARD_MAX_OUTPUT_TOKENS=16384
# Сколько символов расшифровки передавать в агент документа

# Словарь
GLOSSARY_FILE_PATH=./data/glossary.json
# Включить чанковую сверку протокола против диалога (после фикса #1 — рекомендуется протестировать)

```

### ⚠️ Важный нюанс про промпты
`getPrompt()` всегда отдаёт промпт из файла, **но** `resolveSystemPrompt` сначала берёт промпт, **выбранный пользователем в UI** (если он есть в БД). Если кто-то редактировал/выбирал промпт через интерфейс — правка файла на него не повлияет. Тогда нужно в UI выбрать дефолтный промпт (или очистить `selectedPrompt` у пользователя).

## 6. Модели и инфраструктура

**Ollama → vLLM при росте числа пользователей — да.** Ollama обрабатывает запросы очередью (FIFO) без continuous batching: при 10 параллельных ~148 tok/s против ~485 у vLLM, при 50 — разрыв 6–9x, и Ollama начинает ронять запросы и упирать time-to-first-token в секунды. Для «много одновременных пользователей» это решающий аргумент в пользу vLLM (continuous batching + PagedAttention).

**Нюанс вашего железа:** 3090 (24 ГБ) + 3070 (8 ГБ) — разнородные карты. Tensor-parallel в vLLM хочет одинаковые GPU. Реалистичный план: модель целиком на 3090, 3070 — под вспомогательное (классификатор/эмбеддинги RAG). 12–14B в 4-бит (AWQ) комфортно влезает в 24 ГБ с запасом под KV-cache.

**Модель.** На один RTX 3090 оптимум — **Qwen3-14B (AWQ 4-бит)**: по бенчмаркам тянет уровень Qwen2.5-32B, сильное следование инструкциям, на ~15% меньше галлюцинаций. Это лучше по качеству, чем 9B, и при этом батчится на vLLM. Ваш `qwen3.5:9b` существует и новее — да, минорные версии обычно лучше при тех же параметрах; если доступна **Qwen3.5-14B**, она предпочтительнее. Логика: качество решает 14B, а конкурентность — vLLM-батчинг, а не размер модели. За 30B гнаться не нужно.

Практический порядок: сначала новый (короткий) промпт + фиксы, потом замер моделей — на старом промпте-монстре любая мелкая модель страдала, и сравнение было бы нечестным.
