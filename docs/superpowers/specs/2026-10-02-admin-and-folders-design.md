# Администрирование пользователей и проектные папки

Дата: 2026-10-02
Статус: утверждён к реализации

## Запрос заказчика

Переписка 23–24.09.2026:

- нужен администратор: добавление и блокировка доступа к протоколеру, назначение
  прав (админ/пользователь), удаление пользователей;
- проектные папки: администратор создаёт общие папки, пользователь заходит в
  нужную и создаёт там чат. **Пользователь видит только свои чаты**;
- пользователь может завести себе личные папки, невидимые остальным;
- в папку можно прикрепить источники «как в проектах ChatGPT», и протоколер
  учитывает накопленный контекст папки в следующих протоколах.

## Что есть сейчас

- Вход по логину и паролю, scrypt, подписанная httpOnly-сессия
  (`lib/auth-session.ts`). В cookie только `userId` и срок.
- `users` — без ролей и статуса. Регистрация открыта всем (`/api/auth`,
  `action: 'register'`).
- `conversations.user` — владелец; `getConversations` уже фильтрует по нему.
- RAG-сервис изолирует индекс по произвольной строке `conversation_id`
  (это имя каталога в `rag-api/uploads`).
- `/api/rag/upload` и `/api/rag/documents` **не проверяют сессию вообще**:
  зная id диалога, можно читать и удалять его документы. Закрываем попутно.

## Принятые решения

| Развилка | Решение |
|----------|---------|
| Появление пользователей | Только администратор создаёт учётку (логин + временный пароль). Самостоятельная регистрация выключена |
| Первый администратор | `ADMIN_USERNAMES` в env (через запятую). Такой логин может зарегистрироваться сам, если его ещё нет в БД, и всегда имеет роль admin |
| Память папки | Источники (RAG-индекс папки) + текстовые «инструкции папки». Автосбора из чужих чатов нет |
| Просмотр чужих чатов админом | Нет. Админ видит количество чатов и последнюю активность, но не содержимое |

### Почему без автопамяти из чатов

В общей папке работают разные пользователи. Если готовые протоколы
автоматически попадают в индекс папки, ФИО и решения из протокола одного
пользователя всплывают в ответах другому. Это прямо противоречит «пользователь
не видит чужих чатов» и создаёт лишний доступ к ПДн (152-ФЗ). Контекст папки
пополняется осознанно: управляющий папкой загружает источники и пишет
инструкции («заказчик — АО …, протоколы подписывает …, сокращения: …»).

### Почему блокировка проверяется по БД на каждом запросе

Сессия — подписанный токен на 30 дней без серверного хранилища. Если смотреть
только на подпись, заблокированный пользователь работает ещё месяц.
Поэтому `requireUser(req)` после проверки подписи читает запись пользователя:
нет записи или `blocked = true` → 401. Это один `SELECT` по id на запрос, что
дёшево по сравнению с вызовом LLM.

## Модель данных

### users (новые поля)

```
DEFINE FIELD role      ON users TYPE option<string> ASSERT $value = NONE OR $value IN ['admin','user'];
DEFINE FIELD blocked   ON users TYPE option<bool>;
DEFINE FIELD lastLogin ON users TYPE option<datetime>;
```

`option<…>`, а не строгий тип с DEFAULT: у существующих записей полей нет,
и строгий тип ронял бы любой `merge` по ним (пересчёт хеша пароля при входе).
NONE трактуется как `user` / не заблокирован; при старте выполняется бэкфилл.
**Эффективная роль** = `admin`, если логин есть в `ADMIN_USERNAMES`, иначе
`users.role`.

### folders (новая таблица)

```
DEFINE TABLE folders SCHEMAFULL;
DEFINE FIELD name         ON folders TYPE string;
DEFINE FIELD kind         ON folders TYPE string ASSERT $value IN ['shared','personal'];
DEFINE FIELD owner        ON folders TYPE option<record<users>>;  -- только personal
DEFINE FIELD instructions ON folders TYPE string DEFAULT '';
DEFINE FIELD created      ON folders TYPE datetime DEFAULT time::now() READONLY;
DEFINE FIELD updated      ON folders TYPE datetime VALUE time::now();
```

### conversations

Таблица SCHEMALESS, добавляется поле `folder: record<folders>`. Его отсутствие
означает «Без папки» (все существующие чаты).

## Права

| Действие | Кто |
|----------|-----|
| Видеть общую папку и её источники/инструкции | любой активный пользователь |
| Создавать/править/удалять общую папку, её источники и инструкции | admin |
| Видеть и управлять личной папкой | только владелец (админ — нет) |
| Видеть чат | только владелец чата, в любой папке |
| Создать чат в папке / перенести чат в папку | владелец чата, если папка ему видна |

Удаление папки не удаляет чаты: они остаются у владельцев и попадают в
«Без папки».

Ограничения администрирования:

- нельзя заблокировать, удалить или понизить себя;
- нельзя заблокировать, удалить или понизить пользователя из
  `ADMIN_USERNAMES` (роль задана конфигом, UI это показывает);
- удаление пользователя каскадно удаляет его чаты, `anonymization_mappings`,
  `protocol_instructions`, личные промпты и личные папки. RAG-индексы удалённых
  чатов и папок остаются на диске (у RAG-сервиса нет удаления индекса целиком;
  так же ведёт себя удаление одиночного чата сегодня).

## API

### Аутентификация (`/api/auth`)

- `GET` — текущий пользователь `{ id, username, role }` или 401. Клиент
  вызывает при загрузке: обновить роль и узнать о блокировке.
- `POST register` — 403 «Учётные записи выдаёт администратор», кроме логинов
  из `ADMIN_USERNAMES`, которых ещё нет в БД.
- `POST login` — заблокированному: 403 «Доступ заблокирован администратором».
  Ответ содержит `role`.
- `POST change-password` — `{ currentPassword, newPassword }`, для смены
  временного пароля.

### Администрирование (`/api/admin/users`, только admin)

- `GET` — список: `id, username, role, blocked, roleFromEnv, created,
  conversationsCount, lastActivity`.
- `POST` — `{ username, password, role }` — создать.
- `PATCH` — `{ userId, role? , blocked?, password? }`.
- `DELETE` — `{ userId }`.

### Папки (`/api/folders`)

- `GET` — видимые папки: общие + свои личные, с флагом `canManage`.
- `POST` — `{ name, kind }`. `shared` — только admin.
- `PATCH` — `{ folderId, name?, instructions? }` — `canManage`.
- `DELETE` — `{ folderId }` — `canManage`.
- `GET /api/folders/sources?folderId=` — список источников (видимость).
- `POST /api/folders/sources?folderId=` (multipart `file`) — загрузка
  (`canManage`).
- `DELETE /api/folders/sources` — `{ folderId, id }` (`canManage`).

Источники лежат в RAG под scope `folder_<id папки>`.

### Чаты (`/api/conversations`)

- `POST` принимает `folderId`; папка должна быть видна пользователю.
- `PUT` принимает `folderId` (строка — перенести, `null` — убрать из папки).
- Ответы содержат `folderId`.

### RAG (`/api/rag/*`)

Требуют сессию; `conversation_id` должен принадлежать пользователю
(`assertConversationOwnership`).

## Чат: контекст папки

`/api/chat` берёт папку **из записи диалога в БД**, а не из тела запроса.
Если папка есть:

1. **Инструкции папки** добавляются в системный промпт отдельным блоком
   («Контекст проекта … — справка, не замена регламенту»).
2. **Источники папки**: запрос в RAG со scope папки по тексту последнего
   сообщения пользователя (до 1000 символов). Фрагмент ≥ 80 символов добавляется
   в тот же блок. Не зависит от переключателя RAG в интерфейсе диалога.

Блок ограничен 12 000 символов (≈5 000 токенов) — инструкции первыми,
фрагменты источников обрезаются.

Облачного режима больше нет (см. ниже), блок папки видит только локальная модель.

## Интерфейс

- **Форма входа:** без вкладки «Регистрация», подпись «Учётную запись выдаёт
  администратор».
- **Сайдбар:** блок «Папки» над списком чатов — «Все чаты», «Без папки»,
  общие папки, «Мои папки» (+ создать личную; админу + создать общую).
  Выбор папки фильтрует чаты; «Новый» создаёт чат в выбранной папке. Возле
  папки — кнопка настроек (источники и инструкции; редактирование для
  `canManage`, просмотр для остальных).
- **Перенос чата:** в меню чата «Переместить в папку».
- **Шапка:** для admin — ссылка «Администрирование» (`/admin`); для всех —
  «Сменить пароль».
- **`/admin`:** таблица пользователей и форма создания; действия — роль,
  блокировка, сброс пароля, удаление (с подтверждением).

## Конфигурация

```bash
ADMIN_USERNAMES=jacob,mashkovskaya   # логины администраторов (через запятую, регистр не важен)
```

Без `ADMIN_USERNAMES` и без пользователей с ролью admin в БД создавать
пользователей некому — сервер пишет в лог предупреждение при старте.

## Уточнение заказчика (02.10.2026) и что изменилось

> «Давайте сделаем регистрацию через админа… админ только логин пользователя
> вносит, а пользователь при первом входе сам придумывает пароль. …в папки
> может дадим самим пользователям возможность добавляться, куда им нужно? Ну и
> чтобы администратор тоже мог в папки добавлять».

### Учётки без паролей от администратора

- Админ заводит **только логин** и роль. Запись создаётся с пустым
  `passwordHash` и `invitedAt = now`.
- Первый вход: пользователь вводит логин без пароля → ответ `409
  needsPassword` → форма просит придумать пароль → `POST /api/auth
  {action: 'set-initial-password'}`. Пароль сохраняется атомарно
  (`UPDATE … WHERE passwordHash = ''`), так что двое одновременно его не
  перехватят, и пользователь сразу входит.
- **Риск:** пока пароль не придуман, войти под логином может любой, кто его
  знает. Поэтому приглашение живёт **14 дней** (`INVITE_TTL_DAYS`), а админ
  видит статус «Ждёт первого входа · до …» и сразу копирует готовый текст
  приглашения.
- «Сбросить пароль» у админа возвращает учётку в то же состояние: пароли
  администратор больше не задаёт и не знает. Себе и админам из
  `ADMIN_USERNAMES` сбросить нельзя.

### Папки по членству

- `folders.members: option<array<record<users>>>` — участники общей папки.
- **Работать в общей папке** (создавать чаты, видеть источники и инструкции,
  получать её контекст в чате) могут участники и администраторы.
- **Вступить** может любой активный пользователь, через каталог
  (`GET /api/folders?scope=catalog`, `POST /api/folders/membership`). Членство
  здесь наводит порядок в списке проектов, а не делает папку секретной.
- **Админ** добавляет и убирает участников в настройках папки
  (`/api/folders/members`). Создавший папку админ сразу становится участником.
- В сайдбаре у всех, включая админа, только свои общие папки. Остальные
  доступны в каталоге.
- **Выход из папки** (сам или по решению админа) не удаляет чаты: они
  переезжают в «Без папки».
- Удаление пользователя убирает его из участников всех папок.

## Удаление облачного режима (02.10.2026)

Заказчик: «если устраивает только локальный вариант — лучше убрать». Удалено:
режим «Облако + анонимизация» (переключатель, предпросмотр, `/api/anonymize`,
`lib/anonymization/`), провайдер OpenRouter и флаг `CLOUD_MODE`. Модель —
только локальная. Таблица `anonymization_mappings` остаётся: в ней же хранятся
JSON протоколов для точечных правок, а старые соответствия имён подставляются в
протоколы, сохранённые с плейсхолдерами (`lib/legacy-placeholders.ts`).
