# Вывод DOCX-протокола по корпоративному шаблону заказчика

Дата: 2026-09-06
Статус: согласовано, готово к планированию реализации

## Задача

Заказчик:

> Ещё знаете какой вопрос: а возможно вордовский документ с протоколом выводить с нашим
> оформлением? Т.е. шрифт, выравнивание, колонтитулы и т.п. чтобы по нашему шаблону были.

Приложены два файла в корне репозитория:

- `Шаблон протокола чистый.docx` — пустая форма, авторская вёрстка Word. **Эталон оформления.**
- `Шаблон протокола с комм.docx` — та же форма с пояснениями и примерами данных
  (экспорт из Яндекс.Документов, namespace `vyd:`). **Эталон структуры и заполнения.**

Требование: генерируемый протокол должен абсолютно соответствовать шаблону.

## Текущее состояние

`lib/docx-generator.ts` собирает документ библиотекой `docx` на дефолтных стилях.
Совпадение с шаблоном практически нулевое:

| Параметр | Шаблон | Сейчас |
|---|---|---|
| Шрифт по умолчанию | Verdana 11pt (`sz=22`), тело 10pt (`sz=20`) | Calibri 11pt |
| Выравнивание | по ширине (`jc=both`), красная строка 708 twip | по левому краю |
| Интерлиньяж | 1.15 (`line=276 auto`) | дефолт |
| Страница | A4, поля 1424 / 424 / 1134 / 993 twip, header 284, footer 283 | дефолт (по дюйму) |
| Верхний колонтитул | логотип «Форус» справа, 1704348×610649 EMU | отсутствует |
| Нижний колонтитул | линия + «СтК 2.40.08.02-01» ⇥ «Версия 3.0», 9pt | отсутствует |
| Заголовки разделов | подчёркнутые, 10pt, не жирные | жирные |
| Нумерация разделов | `numbering.xml`, `numId=1`, формат `%1.` | текстом `1.\t` |
| Шапки таблиц | без заливки, центр, не жирные | заливка `D9D9D9`, жирные |
| «Согласовано» | 4 колонки, **без границ** | 2 колонки, с границами |

Дополнительно: DOCX собирается **тремя** несогласованными путями.

1. Сервер — `app/api/chat/agents/document-agent.ts:631` и `:1053` (точечная правка)
   → `generateProtocolDocx(Protocol)` → `data-docx` → base64 в панель.
2. Клиент — `components/document/DocumentPanel.tsx:455` `buildDocxData` →
   `@mohtasham/md-to-docx` из markdown. Срабатывает после ручного редактирования
   и как фолбэк, когда `docxData` не пришёл.
3. Клиент — `components/document/DocumentPanel.tsx:324` `handleDownloadBundle` →
   тот же `md-to-docx`, файл кладётся в zip вместе с вложениями.

Пути 2 и 3 дают оформление, никак не связанное с шаблоном.

## Принятые решения

1. **Шаблон как бинарный ресурс.** Шаблон лежит в репозитории целиком; при генерации
   подменяется только `word/document.xml`, остальные части переносятся байт-в-байт.
   Отвергнуто: ручное воспроизведение стилей на библиотеке `docx` (невозможно точно
   воспроизвести `theme1.xml` и табличные стили `a5`–`a9`); `docxtemplater` (новая
   зависимость, платные модули, тяжёлая настройка циклов во вложенных таблицах).
2. **Сервер — единственный сборщик DOCX.** `@mohtasham/md-to-docx` удаляется с клиента.
   Под ручные правки пишется детерминированный `markdownToProtocol`.
3. **Внедрённые шрифты вырезаются** из ресурса (`word/fonts/*.odttf`, 4.3 МБ; флаг
   `embedTrueTypeFonts` в `settings.xml`; записи `w:embed*` в `fontTable.xml` и
   `fontTable.xml.rels`). Verdana и Arial есть на любой Windows-машине, вид не меняется,
   файл протокола уменьшается с ~2.4 МБ до ~30 КБ.
4. **Переезд на HTML не требуется.** Оформление берётся из самого `.docx`; markdown
   в правой панели остаётся превью для чата.

## Архитектура

Новый модуль `lib/docx-template/`:

| Файл | Ответственность |
|---|---|
| `assets/protocol-template.docx` | «Шаблон протокола чистый.docx» без внедрённых шрифтов |
| `template.ts` | чтение ресурса с диска + кэш в памяти процесса (читается один раз) |
| `style.ts` | все константы оформления: размеры, `numId`, ширины колонок, отступы |
| `ooxml.ts` | примитивы сборки: `p()`, `run()`, `table()`, `cell()`, экранирование XML |
| `protocol-body.ts` | `buildProtocolBodyXml(protocol): string` — единственное место, где `Protocol` превращается в OOXML |
| `render.ts` | `renderProtocolDocx(protocol): Promise<Buffer>` — JSZip: открыть шаблон, подменить `word/document.xml`, вернуть zip |

`lib/docx-generator.ts` схлопывается до обёртки `generateProtocolDocx = renderProtocolDocx`.
Сигнатура сохраняется, вызывающий код в `document-agent.ts` не меняется.

JSZip уже в зависимостях (`jszip@^3.10.1`), новых пакетов не требуется.

### Границы модуля

- `protocol-body.ts` знает только про `Protocol` и `ooxml.ts`; ничего не знает про zip,
  файловую систему и HTTP.
- `render.ts` знает про zip и шаблон; ничего не знает про структуру протокола.
- `template.ts` — единственное место, где происходит чтение с диска.
- `style.ts` не импортирует ничего; правка оформления делается только здесь.

### Что копируется из шаблона без изменений

`[Content_Types].xml`, `_rels/.rels`, `word/_rels/document.xml.rels`, `word/styles.xml`,
`word/numbering.xml`, `word/settings.xml`, `word/webSettings.xml`, `word/fontTable.xml`,
`word/theme/theme1.xml`, `word/header1.xml`, `word/footer1.xml`, `word/media/image1.png`,
`word/footnotes.xml`, `word/endnotes.xml`, `docProps/*`.

`sectPr` (поля страницы, ссылки `rId7`/`rId8` на колонтитулы) переносится из шаблона
в конец генерируемого body без изменений.

### Замечание про `word/fonts`

Вырезание шрифтов делается **один раз, при подготовке ресурса**, а не в рантайме:
`assets/protocol-template.docx` уже кладётся в репозиторий без них. Иначе каждая
генерация платила бы за перепаковку.

## Раскладка тела документа

Все размеры — twip, `sz` — полуочки. Значения взяты из `Шаблон протокола чистый.docx`.

| Блок | Формат |
|---|---|
| `ПРОТОКОЛ №{n} ОТ {дата}` | `jc=center`, `ind firstLine=0`, `spacing after=160`; run: `b`, размер по умолчанию (11pt) |
| Название протокола | `jc=center`, `ind firstLine=0`, `after=160`; run: `b` |
| `Договор №… от …` | `ind firstLine=0`, `after=160`; run: `sz=20` |
| `Тема договора: …` | `ind firstLine=0`, `after=160`; run: `sz=20` |
| `1. Дата собрания:` | `numId=1 ilvl=0`, `ind left=284 hanging=284`, `line=276 auto`; метка `sz=20 u=single`, значение `sz=20` |
| `2. Повестка:` | то же |
| — пункты повестки | `numId=4 ilvl=0`, `ind left=644 hanging=360`, `line=276`; `sz=20` |
| `3. Участники:` | `numId=1`, как выше |
| — «Заказчик» / «Исполнитель» | `jc=center`, `ind firstLine=0`, `line=276`; `sz=20`, не жирный |
| — таблицы участников | grid `4672,5388`, `tblW=10060 dxa`, `tblLayout=fixed`, границы `single sz=4 color=000000` со всех сторон и внутри, **без заливки**; шапка «ФИО» / «Должность» — `jc=center`, `sz=20`, не жирная |
| `4. Содержание встречи:` | `numId=1`, как выше |
| — заголовок вопроса | `numId=2 ilvl=0`, `ind left=720 hanging=360`, `line=276`; run `sz=20 b` |
| — `Слушали:` / `Обсудили:` / `Решили:` | `ind firstLine=0`, `line=276`; метка `sz=20 b`, текст `sz=20` |
| `Резюме:` | `ind firstLine=0`, `line=276`, **без номера**; run `sz=20 u=single` |
| — таблица резюме | grid `3810,6255`, `tblW=10065 dxa`, границы как у таблиц участников; шапка «Обсуждаемые вопросы» / «Принятые решения» — `jc=center`, `sz=20`; в ячейке решения метки `Срок:` и `Ответственные:` — `sz=20 b`, каждая отдельным абзацем |
| `5. Согласовано:` | `numId=1`, как выше |
| — таблица подписей | grid `1830,3000,2025,2235`, `tblW=9090 dxa`, `tblInd=284 dxa`, **все границы `nil`** |

Структура таблицы «Согласовано»:

```
ROW 0: [gridSpan=2] "Со стороны Заказчика"      | [gridSpan=2] "Со стороны Исполнителя"
        абзац 2:    "ООО «…»:"                  | абзац 2:     "ООО «…»:"
        оба: jc=center, sz=20, b (заголовок) / sz=20 (организация)

ROW i (по строке на подписанта, i = 1..max(len(custSigs), len(execSigs))):
       [1830] "Фамилия И.О." ind left=66 | [3000] линия подписи
     | [2025] "Фамилия И.О." ind left=317 | [2235] линия подписи
```

Линия подписи воспроизводится так же, как в шаблоне: пустой абзац с `u=single`
в `rPr` (визуально сверяется с эталонным рендером, см. «Приёмка»).

Если у стороны нет подписантов — ячейка ФИО пустая, линия остаётся.

### Отличия от текущего вывода, которые уходят

- Серая заливка `D9D9D9` в шапках таблиц — в шаблоне её нет.
- Жирные заголовки разделов — в шаблоне они подчёркнутые и не жирные.
- `1.\t`, `2.\t` текстом — заменяются на реальную нумерацию Word через `numbering.xml`.
- «Согласовано» из двух колонок с рамками — заменяется на 4 колонки без рамок.
- Суффикс `/______________` после ФИО подписанта — в шаблоне линия лежит в соседней ячейке.

## Ручное редактирование

`lib/protocol-markdown-parse.ts` — `markdownToProtocol(md: string): Protocol`,
детерминированный построчный парсер, обратный к `protocolToMarkdown`
(`app/api/chat/agents/document-agent.ts:1108`). Без обращений к LLM.

Формат входа фиксирован и известен: `ПРОТОКОЛ № … ОТ …`, `**Название**`, блок договора,
`---`, разделы `**N. Заголовок**`, markdown-таблицы участников, `**i) Вопрос**` с
`**Слушали:**` / `**Обсудили:**` / `**Решили:**`, таблица резюме, таблица «Согласовано».

Парсер устойчив к ручным правкам текста внутри блоков; при нераспознанной структуре
секции она заполняется пустым значением, а не роняет разбор.

Парсер обязан снимать визуальные маркеры, которые добавляет `markUnresolvedInMarkdown`
(`document-agent.ts:1078`): значок `⚠️` и хвост «— требует уточнения». Иначе они попадут
в DOCX.

`app/api/download-docx/route.ts` расширяет контракт, оставаясь обратно совместимым:

- `{ content, filename }` — как сейчас: base64 уже собранного файла просто отдаётся;
- `{ markdown, filename }` — новый режим: `markdownToProtocol` → `renderProtocolDocx`.

Ответ (заголовки, `Content-Disposition`) не меняется.

`components/document/DocumentPanel.tsx`:

- удаляются `buildDocxData` и импорт `@mohtasham/md-to-docx`;
- `saveEdit` после ручной правки не пересобирает файл на клиенте, а сбрасывает
  `docxData` в `{ filename }` без `content` — признак «нужна пересборка на сервере»;
- `handleDownloadDocx`: если `docxData.content` есть — шлёт его (обычный путь, файл уже
  собран сервером из `Protocol` через шаблон); если нет — шлёт `{ markdown, filename }`;
- `handleDownloadBundle` берёт байты с того же эндпоинта и кладёт их в zip;
- убирается автогенерация `docxData` на клиенте (`DocumentPanel.tsx:205`); кнопки
  скачивания разблокируются по наличию контента, а не по наличию `docxData`.

Поток `data-docx` из `document-agent.ts` не меняется: он по-прежнему несёт base64,
собранный на сервере из деанонимизированного `Protocol`. Контракт SSE и
`wrapResponseWithDeanonymization` не затрагиваются.

Зависимость `@mohtasham/md-to-docx` удаляется из `package.json`, если других
потребителей не осталось.

## Приёмка

Автоматически (Jest):

- сборка DOCX для эталонного `Protocol` из фикстуры проходит без ошибок;
- в получившемся zip присутствуют `word/header1.xml`, `word/footer1.xml`,
  `word/media/image1.png`, `word/styles.xml`, `word/numbering.xml`, и их содержимое
  побайтно равно содержимому из `assets/protocol-template.docx`;
- `word/document.xml` — snapshot-тест;
- `word/fonts/` в результате отсутствует;
- круговой тест: `markdownToProtocol(protocolToMarkdown(p))` эквивалентен `p`
  для набора фикстур (включая ноль подписантов, разное число подписантов у сторон,
  пустое резюме, многострочные «Обсудили»/«Решили»);
- тот же круговой тест поверх `markUnresolvedInMarkdown(protocolToMarkdown(p))` —
  маркеры `⚠️` и «— требует уточнения» не должны попадать в результат.

Визуально:

- скрипт сверки рендерит эталон и результат через LibreOffice
  (`soffice --headless --convert-to pdf`, далее постранично в PNG) и кладёт картинки
  рядом для сравнения. LibreOffice установлен в среде разработки
  (`C:\Program Files\LibreOffice\program\soffice.exe`).
- эталон для сверки — `Шаблон протокола с комм.docx`, в нём заполнены примеры данных.

## Вне объёма

- Изменение состава полей `Protocol` и правил регламента (`lib/prompts/regulation.ts`).
- Редактирование протокола по полям вместо свободного markdown.
- Поддержка нескольких корпоративных шаблонов и выбор шаблона пользователем.
- Реакция на смену шаблона заказчиком: обновление сводится к замене файла
  `assets/protocol-template.docx` и правке `style.ts`, автоматизация не планируется.
