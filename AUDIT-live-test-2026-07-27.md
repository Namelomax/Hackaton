Стенд: https://hackaton-kappa-seven.vercel.app/ , режим «☁️ Облако + анонимизация», модель `nvidia/nemotron-3-ultra-550b-a55b:free`.

## Что работает

- **Анонимизация**: 15 упоминаний ПДн → 5 плейсхолдеров, даты сохранены (как договорились), деанонимизация в ответе корректная.
- **Маркеры уточнений в документе (п.3 заказчика)** — работают. В сформированном протоколе появились:
  - `учреждение (наименование ⚠️ требует уточнения)`
  - `в рабочем чате (наименование ⚠️ требует уточнения)`
  - `на следующей неделе (⚠️ требует уточнения: конкретная дата)`, `вчера (⚠️ требует уточнения: конкретная дата)`
  - `Срок: ⚠️ требует уточнения` в каждом решении и в резюме
  - `Тема договора: ⚠️ требует уточнения`
- **Финальная сверка** после генерации отдельным сообщением перечисляет относительные даты — полезно.

## Найденные проблемы

### 1. Правка/Retry теряют документ и conversationId (главная причина «правая панель не обновляется»)

Перехват тела запросов `/api/chat`:

| Путь | documentContent | conversationId | selectedPromptId |
|---|---|---|---|
| обычная отправка | есть (5913 симв.) | есть | есть |
| ✏️ правка сообщения / Retry | **нет** | **нет** | **нет** |

Агент не видит текущий протокол → правки применять не к чему.
**Исправлено**: `app/page.tsx` → `buildRetryBody()`, используется в `handleEdit` и `handleRegenerate`.

### 2. Повторная ошибка не показывается вообще (тишина вместо ответа)

`onError` в `app/page.tsx` навсегда запоминал сигнатуру последней ошибки и молча гасил такую же. На стенде: отправка правки → `/api/chat` 500 → **ни ответа, ни ошибки, ни изменений в панели**. Ровно тот симптом, что описывает заказчик.
**Исправлено**: дедуп сведён к окну 3 секунды (эхо одного запроса).

### 3. Ложное «Проверь OPENROUTER_API_KEY»

При 500 Next.js отдаёт HTML-страницу ошибки; парсер подстрок ловил в разметке признаки 401 и показывал ошибку про API key.
**Исправлено**: HTML-страница ошибки распознаётся отдельно, текст про 500 и объём контекста.

### 4. 500 FUNCTION_INVOCATION_FAILED в генерации документа

Логи Vercel: последняя строка перед падением — `[generateFinalDocument] maxOutputTokens=8192`, подпись `FUNCTION_INVOCATION_FAILED`. В соседнем запросе та же причина попала в catch и вернула 200:

```
Document generation error: AI_NoObjectGeneratedError: No object generated: could not parse the response.
text: '', finishReason: 'other'
cause: AI_JSONParseError: Unexpected end of JSON input
```

Модель (бесплатный слаг Nemotron) отдаёт **пустой ответ**. В `document-agent.ts` промис `streamResult.object` подписывался только ПОСЛЕ полного разбора `partialObjectStream`. Когда провайдер отваливается сразу, промис отклоняется в момент, когда подписчика ещё нет → unhandledRejection → Vercel убивает функцию, клиент получает 500 и HTML вместо стрима. Try/catch вокруг не помогает: реджект вне его цепочки.

**Исправлено**:
- обработчик к `streamResult.object` вешается сразу после `streamObject(...)` (`objectSettled`), разбор результата — как раньше, но уже из settled-значения;
- пустой ответ модели даёт понятное сообщение вместо стектрейса;
- при падении генерации в правую панель возвращается предыдущая версия протокола (раньше `data-clear` уже прошёл и документ терялся).

### 5. Протоколер не делает документ после первого круга вопросов

Договорённость с заказчиком: после первичных вопросов по структуре — сразу документ, дальше уточнения по тексту. Фактически агент задал **два** круга вопросов и сформировал протокол только после прямого «больше вопросов не задавай». Причина — «Поток диалога» в `SGR_MAIN_AGENT_PROMPT`: Шаг 2 (сроки/ответственные) и Шаг 3 (подписанты) блокировали генерацию.
**Исправлено в промте** (`lib/prompts/sgr-prompts.ts`): Шаг 2 = повестка + немедленный вызов инструмента, недостающее уходит в документ как «⚠️ требует уточнения»; Шаг 3 = уточнения уже по готовому документу (включая подписантов). Требует проверки после деплоя.

### 8. Правка уточнений переписывала весь документ → режим точечного patch

Проверка на задеплоенной версии: правка трёх мест («учреждение — Министерство финансов», «чат проекта в Telegram», «срок 24.07.2026») применилась верно, 500 не было, но диффом видно **31 изменённую строку из 76**. Само по себе поехало:

- «Соколова Ирина» → «Ирина Соколова» во всех таблицах;
- «⚠️ требует уточнения» → «⚠️ подлежит уточнению»;
- «Заказчик (Соколова Ирина) открыла совещание…» → «Заказчик открыл совещание…» (ФИО исчезли);
- перетасован порядок людей в «Слушали».

Причина: каждый вызов `publishInvestigationProtocol` пересобирает весь Protocol JSON через `streamObject`. Текущий документ подставляется в промпт лишь как контекст.

**Сделано — patch-режим** (`app/api/chat/agents/protocol-patch.ts`):

1. После каждой полной генерации валидный Protocol JSON сохраняется в `conversations.document_json` (`saveConversationProtocolJson`).
2. При следующей правке модель не пишет документ заново, а возвращает список замен `find → replace` по текущему тексту (`planProtocolPatch`, `generateObject`, temperature 0).
3. Замены применяются детерминированно к строковым полям Protocol JSON. Требование строгое: каждая подстрока встречается **ровно один раз**, иначе патч отменяется целиком.
4. Любой сбой — планировщик не смог, фрагмент не найден, встречается дважды, результат не прошёл Zod — откат на прежнюю полную генерацию.
5. Из патченного объекта детерминированно пересобираются markdown и DOCX, поэтому незатронутые места байт в байт прежние.
6. В облачном режиме и документ, и текст правки уходят в модель обезличенными, результат деанонимизируется перед DOCX и сохранением.
7. Выключается через `PROTOCOL_PATCH_MODE=off`.

Логика замен покрыта проверкой: уникальная замена применяется, соседний одинаковый фрагмент не трогается, неоднозначная и ненайденная строки дают отказ, исходный объект не мутируется.

**Важно**: `document_json` появляется только после первой полной генерации на новой версии. В уже существующих чатах первая правка ещё раз пересоберёт документ, дальше пойдут точечные.

### 9. Причина пустого ответа модели (AI_NoObjectGeneratedError)

Первый заход закрыл только последствия (не падала функция, документ не терялся). Сама причина — бюджет вывода:

- `generateFinalDocument` брал `ollamaProtocolMaxOutputTokens()` = **8192** и для локальной, и для облачной модели;
- для reasoning-модели это общий бюджет на размышления **и** JSON. Рассуждения съедали его целиком → `text: ''`, `finishReason: 'other'` → `AI_JSONParseError: Unexpected end of JSON input`;
- отсюда и «через раз»: короткие рассуждения — протокол собирается, длинные — пусто;
- `reasoning: { enabled: false }` передавался, но на моделях, где размышления не отключаются переключателем, он ничего не даёт.

**Сделано:**

1. `cloudProtocolMaxOutputTokens()` — отдельный бюджет для облака, по умолчанию 32000 (env `CLOUD_PROTOCOL_MAX_OUTPUT_TOKENS`). Локальный путь по-прежнему 8192.
2. К `reasoning` добавлен `exclude: true` — где отключить нельзя, рассуждения хотя бы не попадают в ответ и не ломают разбор JSON.
3. Один автоматический повтор без стриминга при пустом ответе. Через `OPENROUTER_FALLBACK_MODELS` (список слагов через запятую) повтор уходит на запасную модель средствами роутинга OpenRouter.
4. Разбор ошибки в лог: `finishReason`, длина и превью текста, `inputTokens/outputTokens/reasoningTokens`. Раньше в Vercel было видно только `usage: [Object]`.

**Проверка гипотезы**: если пустой ответ повторится, в логе теперь будет видно `reasoningTokens` — если он близок к бюджету, диагноз подтверждён окончательно.

### 10. Бюджет вывода для локальной модели и «старый документ — основа»

- `ollamaProtocolMaxOutputTokens()` поднят с 8192 до **32000** (env `OLLAMA_PROTOCOL_MAX_OUTPUT_TOKENS`). У qwen3 это тоже общий бюджет на размышления и JSON — длинный протокол обрывался.
- Добавлена страховка по окну: если задан `OLLAMA_CONTEXT_LENGTH`, бюджет ответа не превысит 40% окна (иначе Ollama молча срезает начало промпта вместе с системными инструкциями). При `num_ctx=32768` бюджет автоматически станет 13107.
- `ollamaHardCapOutputTokens()` больше не может оказаться ниже бюджета протокола (было 16384 против 32000 — срезало бы молча). Теперь `max(32768, бюджет)`.
- В `SGR_DOCUMENT_AGENT_PROMPT` добавлен блок «ГЛАВНОЕ ПРАВИЛО ПРИ ПОВТОРНОЙ СБОРКЕ»: существующая версия — база, все незатронутые поля переносятся дословно (порядок ФИО, порядок в «Слушали», формулировка маркера), перефразировать по своей инициативе запрещено. Исключение — явная ошибка (противоречие расшифровке, ФИО, которого в ней нет, пустой обязательный раздел): исправить и перечислить исправленное отдельно.
- Заголовок блока существующего документа в промте переписан с «пользователь редактировал вручную» на прямую инструкцию использовать его как базу.

Это подстраховка на случай, когда patch-режим отказал и идёт полная пересборка.

### Патч-режим на этом прогоне не сработал — и почему

В чате было обычное «Протокол сформирован и отправлен в правую панель», а не «Правка внесена точечно». То есть 2 строки из 76 — заслуга нового правила промта, а не патча.

Причина: планировщику показывался markdown, пропущенный через `markUnresolvedInMarkdown`, то есть со значком ⚠️. В полях Protocol JSON значка нет — он навешивается только при отрисовке. Модель копировала `find` вместе со значком, поиск не находил фрагмент, и патч честно откатывался на полную генерацию. При этом каждая типовая правка — это как раз уточнение места с маркером, так что патч не срабатывал бы почти никогда.

**Исправлено:**

1. Планировщик получает сырой `protocolToMarkdown` без значков.
2. В промт планировщика добавлено: значок ⚠️ в `find` не писать, брать текст, а не разметку.
3. В `applyEditsToProtocol` — подстраховка: если `find` не найден, повторный поиск с вычищенными ⚠️ и схлопнутыми пробелами.

Проверено тестом: `find` со значком теперь применяется, `find` без значка применяется, мусорный `find` по-прежнему откатывает патч целиком.

### 11. Даты считает код + косметические гарды

Новый модуль `lib/date-context.ts`:

- `buildDateContextBlock()` — единая справка о сегодняшней дате для чат-агента **и** агента документа (раньше блок был только в чате, поэтому агент документа не мог посчитать «в четверг»). В тексте блока прямо сказано: это дата обработки, а не дата встречи.
- `resolveRelativeDatesInText(text, anchor)` — детерминированный перевод относительных выражений в ДД.ММ.ГГГГ от даты встречи.

Новые гарды в `lib/protocol-guards.ts` (порядок применения важен — после `enforceDateProvenance`, иначе он сотрёт вычисленные даты как «отсутствующие в расшифровке»):

| Гард | Что делает |
|---|---|
| `resolveRelativeDates` | «в четверг» → 30.07.2026, «до конца недели» → до 24.07.2026, «на следующей неделе» → до 31.07.2026, «вчера» → 22.07.2026, «до конца месяца» → до 31.07.2026. Каждая вычисленная дата попадает в финальную сверку с пометкой «рассчитано от даты встречи — проверьте» |
| `dropInventedMeetingDate` | дата встречи = сегодняшняя и её нет ни в расшифровке, ни в ответах → «требует уточнения» + предупреждение |
| `normalizeProtocolNumbers` | «№№14» → «14» (знак добавляет рендер) |
| `unifyUnresolvedMarkers` | «подлежит уточнению» и «подлежащий уточнению» → единое «требует уточнения» |
| `dedupeParticipants` | «Сергей»/«Сергея» → одна запись: ФИО из первой (именительный падеж), должность из той, где заполнена |

Неоднозначные обороты («скоро», «в ближайшее время», «на днях») намеренно не вычисляются — их по-прежнему помечает `flagRelativeDates`.

Проверено на данных: 23.07.2026 (четверг) как якорь даёт все перечисленные выше даты; «в ближайшее время» не тронуто; дедуп не склеивает «Иванов Иван» и «Иванова Мария».

Также поднят локальный бюджет вывода до 32000 (см. п.10) и обновлён `SGR_MAIN_AGENT_PROMPT`: относительные выражения в протоколе запрещены, дату из блока контекста нельзя ставить датой встречи, маркер один.

### 12. Прогон после гардов: два перегиба, оба поправлены

Что пошло не так на чистом чате:

1. **Агент собрал документ на первом же ходе**, не задав ни одного вопроса — правило «после первого круга сразу документ» модель применила ещё агрессивнее. Заказчик хотел сначала подтвердить шапку и участников. → В промт добавлен прямой запрет вызывать инструмент на первом ходе после расшифровки (исключение — прямая команда «сделай протокол сразу»).
2. **Даты исчезли вместо того, чтобы стать конкретными.** Цепочка развалилась так: даты встречи в расшифровке нет → `dropInventedMeetingDate` честно ставит «требует уточнения» → у `resolveRelativeDates` нет якоря → «в четверг» не вычисляется → модель подставляет свою дату → `enforceDateProvenance` стирает её как отсутствующую в расшифровке. Итог: «подлежит уточнению» вместо даты.

   Исправлено двумя правками:
   - у `resolveRelativeDates` появился запасной якорь — дата обработки, если даты встречи нет. Такие расчёты помечаются отдельно: «рассчитано от сегодняшней даты — дата встречи неизвестна»;
   - вычисленные даты передаются в `enforceDateProvenance` как привилегированные, поэтому он их больше не стирает. Порядок теперь: `dropInventedMeetingDate` → `resolveRelativeDates` → `enforceDateProvenance`.
3. **`ПРОТОКОЛ № требует уточнения`** в шапке — модель отправила в «уточнения» и номер протокола. → Гард `ensureProtocolNumber`: пустой номер или маркер → «1» с пометкой в сверке.

Проверено на данных: без даты встречи «в четверг» → 30.07.2026, «до конца недели» → до 31.07.2026, провенанс-гард стирает 0 дат, номер протокола становится 1.

**Что сработало правильно в этом прогоне:** дата встречи больше не подставляется сегодняшней (`dropInventedMeetingDate` отработал), документ формируется без второго круга вопросов, в чате перечислены все места с маркером.

### 13. «Ошибка анонимизации: Unexpected token 'A'» — что это на самом деле

Симптом: тост с сырым `SyntaxError: Unexpected token 'A', "An error o"... is not valid JSON`, следом чат-запрос висит и заканчивается «Истекло время ожидания ответа».

Диагноз: `/api/anonymize` не отвечает. Прямой запрос к нему из браузера висел больше 45 секунд без ответа. Когда платформа обрывает зависшую функцию, она отдаёт СВОЙ текст «An error occurred…» — не JSON. Клиент вызывал `res.json()` и падал на разборе, показывая пользователю внутреннюю ошибку парсера вместо понятного сообщения. Первопричина — сам сервис анонимизации (jupiter) не отвечает или крайне медленный.

**Исправлено (обработка, не первопричина):**

1. Клиент читает тело как текст и парсит защищённо: не JSON → тост «Анонимизатор не ответил, вероятно таймаут. Отправляю через локальную модель» и честный fallback вместо `SyntaxError`.
2. На сервере у `/api/anonymize` появился бюджет всего запроса (`ANONYMIZE_ROUTE_BUDGET_MS`, по умолчанию 110 сек, заметно меньше `maxDuration=300`). Не уложились — возвращаем корректный JSON 503, UI уходит на локальную модель, а не ждёт обрыва платформы.

**Первопричину надо чинить на стенде**: проверить, жив ли сервис анонимизации на jupiter и сколько он реально отвечает на расшифровке 3 КБ. Пока он молчит, облачный режим не протестировать.

### 14. Финальный прогон: цикл заказчика проходит

| Проверка | Результат |
|---|---|
| Первый ход — только вопросы, документа нет | ОК (запрет в промте работает) |
| Дата встречи не подставляется сегодняшней | ОК, «⚠️ требует уточнения», спрашивается в блоке вопросов |
| После ответа с пробелами документ собирается сразу | ОК, второго круга вопросов нет |
| Номер протокола | ОК, №1 (гард), не «требует уточнения» |
| «Договор №№14» | ОК, теперь «Договор №14» |
| Единый маркер | ОК: «подлежит уточнению» — 0 вхождений, «требует уточнения» — 18 |
| Дубль «Сергей»/«Сергея» | ОК, 0 дублей (анонимизатор свернул склонение в один плейсхолдер) |
| Относительные даты после уточнения даты встречи | «до конца недели» → 25.07.2026, «в четверг» → 30.07.2026, «вчера» → 22.07.2026, «позавчера» → 21.07.2026, список показан в чате |
| Правка (дата встречи + учреждение + чат) | Применена корректно, изменилось 11 строк из 84 |

**Осталось два хвоста:**

1. **«назначена на четверг» пережило замену.** Регулярка дней недели требовала предлог «в/во», а в тексте было «на». Исправлено: предлоги в/во/на, при этом «назначена НА четверг» → «назначена НА 30.07.2026» (предлог сохраняется), а «встреча В четверг» → «встреча 30.07.2026» (с датой предлог лишний). Отдельно поймал грабли: `\b` в JS не работает с кириллицей.
2. **Патч-режим по-прежнему не подтверждён.** В чате не было сообщения «Правка внесена точечно», изменилось 11 строк вместо 2–3. Нужна строка `[protocol-patch]` из логов, чтобы понять: не нашёлся `document_json`, планировщик отказал или замены не применились.

## Не исправлено, на заметку

- **«Всегда локальная модель» при правке**: клиент отправляет `chatProvider: "openrouter"` корректно (проверено перехватом). Переключение происходит на сервере — `app/api/chat/route.ts:894-902`: если анонимизатор недоступен, провайдер молча меняется на `ollama` с уведомлением «отвечаю через локальную модель». На пути правки/Retry клиентский preview `/api/anonymize` не вызывается, весь текст анонимизируется внутри запроса — при таймауте сервиса это срабатывает чаще.
- **Правка/Retry в облачном режиме не показывают окно «Проверка перед отправкой в облако»**, хотя галочка включена. Анонимизация на сервере выполняется, но подтверждения пользователь не видит.
- **Имена из чата не мапятся на плейсхолдеры**: на «Сергея включай» модель ответила «Сергея в расшифровке не встречается» — в облако ушёл `[PERSON_4]`, а склонённое «Сергея» не подставилось. Нужна морфологическая нормализация при forward-подстановке.
- **Путаница сторон**: Дмитрий Величко в таблице «Заказчик», а в тексте раздела 4 — «Исполнитель (Дмитрий Величко)».
- **Retry затирает готовый протокол** в правой панели на время генерации; при падении запроса документ остаётся пустым.

## Проверить после деплоя

1. Правка сообщения → в теле `/api/chat` есть `documentContent` → панель обновляется.
2. Две одинаковые ошибки подряд → обе видны в чате.
3. Ответ на первый блок вопросов → документ формируется сразу, без второго круга.
4. Генерация протокола 3–5 раз подряд на облачном слаге: 500 не должно быть ни разу — при пустом ответе модели ожидается сообщение в чате и сохранённая прошлая версия документа.
5. Patch-режим: сформировать протокол → уточнить одно место → диффом убедиться, что изменились только строки правки. В логах ожидается `[protocol-patch] применено замен: N (без пересборки документа)`; при отказе — строка с причиной и обычная генерация.
6. Прогнать `npm run build` локально (полный typecheck в песочнице не успел завершиться).
